Git history shows the original version at commit 661a756 submitted the full
queue to one ThreadPoolExecutor and used future.result() without a timeout.
That version could hang when one or more worker threads stalled below the
requests timeout layer or when many slow sites accumulated socket pressure.

Git history also shows commit 106833f ("fix: rewrite backfill_emails.py to
prevent hangs at high volume") already changed the script to the current
batched, guarded implementation.

ROOT CAUSE HYPOTHESIS
--------------------------------------------------
The most likely root cause of the originally reported hang was the old
ThreadPoolExecutor design, not a single consistently bad row-300 URL:
- The original script submitted up to 1100+ futures at once.
- It used one global as_completed(timeout=600) ceiling.
- It called future.result() with no per-future timeout.
- It only wrote to Sheets after extraction completed.
- A worker stalled in DNS/TCP/SSL/read handling could keep the executor from
shutting down cleanly.
- With many pending futures, slow sites could accumulate and make the process
appear to hang around whichever row was next in progress output.

The report that --resume gets past row 300 and then hangs elsewhere supports
this hypothesis: the problem follows the executor/network workload, not one
specific row.
